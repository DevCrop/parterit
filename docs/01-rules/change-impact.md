# 요구사항 변경 → 파급효과 분석 절차

> 고객 요청이 중간 또는 마지막에 바뀐 경우, 어디서부터 영향이 시작되는지 추적하는 절차.

## 1. 변경 분류

먼저 변경이 어느 레이어에서 시작되는지 식별:

| 변경 레이어 | 영향 받는 하위 레이어 |
|---|---|
| **브랜딩 변경** | 디자인 → 퍼블 → 개발 (전체 재검토) |
| **기획 변경** | 디자인 → 퍼블 → 개발 |
| **디자인 변경** | 퍼블 → 개발 |
| **퍼블 변경** | 개발 (마크업 구조 의존 시) |
| **개발 변경** | 서버 (API/배포 영향 시) |
| **서버 변경** | — (최하위) |

> **상위 레이어가 바뀌면 하위 레이어는 모두 재검토 대상**.

## 2. 분석 절차 (5단계)

### Step 1: 기록
- `docs/04-history/requirement-changes.md` 최상단에 변경 내용 + 일시 + 사유 추가

### Step 2: 분류
- 위 표에서 변경 레이어 식별

### Step 3: 영향 범위 매핑
영향받는 각 레이어마다 다음을 확인:
- 어떤 파일이 영향받는가? (`workspace/` 내)
- 어떤 문서가 영향받는가? (`docs/02-variables/` 위주)
- 어떤 에이전트 지침이 영향받는가? (`.claude/agents/`)

### Step 4: 실행 계획 수립
- 영향받는 항목들을 **상위 → 하위** 순서로 처리
- 각 항목마다 담당 역할의 에이전트 가이드 따름
- **이 절차는 항상 직렬** — 병렬 디스패치 금지(상위 산출물이 하위 입력이므로). 상세: `docs/01-rules/parallel-work.md`

### Step 5: 통합 검증
- 모든 변경 적용 후 전체 일관성 확인
- `must-check.md` 전체 항목 재실행
- `patch-notes.md`에 통합 결과 1줄 기록

## 3. 예시

> 고객이 "메인 컬러 빨강 → 파랑으로 바꿔주세요" 요청

1. **기록**: requirement-changes.md에 "2026-05-12: 메인 컬러 R → B"
2. **분류**: 브랜딩 변경
3. **영향 범위**:
   - `docs/02-variables/brand-guide.md` (컬러 토큰)
   - `workspace/src/styles/` (CSS 변수)
   - 디자인 시안 전체
   - 로고가 컬러 의존이면 로고도 영향
4. **실행**: brand-guide.md 수정 → 시안 업데이트 → CSS 변수 변경 → 컴포넌트 확인
5. **검증**: 모든 화면에서 새 컬러 반영 확인, patch-notes.md 기록

## 4. 변경 거부 기준

다음 경우 즉시 사용자에게 알리고 작업 보류:
- 변경이 `goals.md`의 핵심 목표를 흔드는 경우
- 변경이 `server-spec.md`의 기술 제약과 충돌하는 경우
- 변경 작업량이 기존 작업의 30% 이상 폐기를 요구하는 경우
