# 병렬 작업 / 서브에이전트 디스패치

> 명령이 **여러 역할·여러 하위작업**에 걸치면 — 각각을 **트랙(track)**으로 보고 **기본은 병렬**(트랙당 서브에이전트 1명)로 돌려 생산성을 올린다.
> 단, **겹침·오염·중복 위험**이 보이면 그 트랙들만 **직렬**로 떨어뜨린다. 이 파일은 그 판정 기준과 디스패치 패턴.
>
> 큰 그림은 `roles.md`(레이어 모델) 위에 얹는다 — **같은 레이어 = 병렬 가능 / 레이어 의존 = 직렬.**

---

## 1. 병렬 vs 직렬 판정

### 트랙을 병렬로 돌리려면 — **아래 4개를 전부** 만족해야 한다

1. **쓰기 범위(write-scope)가 안 겹친다** — 각 트랙이 *만들고 수정할 파일·폴더 경로*를 미리 선언했고, 트랙끼리 그 경로가 교집합이 없다.
2. **레이어 의존이 없다** — `roles.md` 매트릭스(브랜딩 → 기획 → 디자인 → 퍼블 → 개발 → 서버)에서, 한 트랙의 산출물을 다른 트랙이 *입력으로* 쓰면 의존 관계 → 직렬.
3. **공유 상태를 동시에 안 건드린다** — 같은 DB 스키마/마이그레이션, 같은 `docs/02-variables/brand-guide.md` 토큰, 같은 설정 파일, 같은 컴포넌트.
4. **`docs/04-history/*`에 쓰지 않는다** — append-only 히스토리(`patch-notes`·`requirement-changes`·`decisions`)는 동시에 쓰면 항목이 엉킨다. 트랙은 거기 안 쓴다 — 기록은 **메인이 마지막에 한 번만**.

하나라도 어기면 → **그 트랙들만 직렬** (순서대로 처리). 그 외 독립 트랙은 계속 병렬로 갈 수 있다.

### 항상 직렬 — 예외 없음

- **요구사항 변경 처리**(`change-impact.md`) — 언제나 **상위 → 하위 순서로 직렬**. 병렬 작업 중 요청이 바뀌면 영향 트랙을 멈추고 5단계 절차로 전환.
- 같은 파일을 두 트랙이 수정 / append-only 파일 쓰기 / 레이어 의존 체인.

### 실패 모드 → 처방

| 위험 | 증상 | 처방 |
|---|---|---|
| 같은 파일 동시 수정 | 두 서브에이전트가 같은 경로에 write | 그 두 트랙만 직렬. 또는 한 트랙이 인터페이스/스켈레톤만 만들고 합류 후 나머지 |
| append-only 경합 | `patch-notes.md` 등에 동시 append → 항목 섞임·유실 | 트랙은 히스토리에 안 쓴다. 메인이 결과를 모아 **마지막에 1줄**(`/patch-note`) |
| 레이어 의존 위반 | 디자인 안 끝났는데 퍼블 시작 | `roles.md` 순서대로 직렬 — 상위 끝나면 하위 디스패치 |
| 공유 상태 충돌 | 두 트랙이 같은 DB 스키마/브랜드 토큰 변경 | 그 변경을 **한 트랙으로 합치고**, 나머지는 그 산출물을 입력으로 받음(= 직렬) |
| 중간 요구사항 변경 | 작업 도중 요청이 바뀜 | 무조건 `change-impact.md` 5단계, 상위→하위 직렬. 진행 중이던 병렬 트랙 중 영향받는 건 중단 |

## 2. 서브에이전트 디스패치 패턴

### 각 트랙(서브에이전트)에게 **반드시** 줄 것 — 미니 작업명세

- **목표** — 한 줄: 무엇을, 왜
- **소유 경로(쓰기 범위)** — 이 트랙이 만들고 수정해도 되는 파일·폴더. **이 밖은 손대지 마라.**
- **읽기 전용 참고** — `.claude/agents/<role>.md` + 그 작업에 직접 관련된 docs + (있으면) 다른 트랙의 산출물 경로
- **금지** — `docs/04-history/*` 쓰기 금지 · 소유 경로 밖 수정 금지 · 사용자 확인 필요 항목(`workflow.md` §4: 기능 동작·디자인/브랜딩·의존성·배포)은 직접 결정하지 말고 메인에 보고
- **보고 형식** — ① 변경한 파일 목록 ② 한 일 요약 ③ 막힌 점 / 비자명하게 결정한 점 ④ 미충족 체크리스트(`must-check.md`)

> 트랙당 서브에이전트는 그 역할의 에이전트 타입을 쓴다 — 개발 트랙 = `developer`, 퍼블 트랙 = `publisher` 등.

### 메인 에이전트가 디스패치 **후에** 하는 것

1. 모든 트랙의 보고 수집
2. **`git status`로 실제 변경 파일 확인** — 선언한 쓰기 범위 안인가? 트랙끼리 겹친 파일이 있나? 겹쳤으면 → 그 부분 직렬로 재작업
3. **통합** — 트랙 산출물을 합치고 경계 일관성 확인(`must-check.md` 관련 카테고리 재점검). 산출물이 서로 모순되면 상위 레이어 트랙을 정본으로.
4. **기록은 메인이 한 번만** — `patch-notes.md`에 1줄(`/patch-note`), 비자명한 결정은 `decisions.md`

---

## 3. 한 줄 요약

> 여러 역할/하위작업 → 각 트랙의 **쓰기 범위를 선언** → 겹치지 않으면 **병렬(서브에이전트)**, 겹치거나·레이어 의존이거나·공유 상태/히스토리면 **직렬**. 끝나면 메인이 `git status`로 겹침을 확인한 뒤 통합·기록한다. 요구사항 변경은 항상 직렬(`change-impact.md`).
