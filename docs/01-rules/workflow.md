# 작업 순서 / 우선순위

> AI가 명령을 받았을 때 따라야 할 절차. **토큰을 아끼면서**(무관한 문서 안 읽기, 왕복 줄이기) 정확히 실행하는 게 목표.

## 1. 명령 접수 (Intake) — 사용자 명령을 받으면 항상

### Step 1. 분류
어느 역할/도메인인가? — **브랜딩 / 기획 / 디자인 / 퍼블 / 개발 / 서버** (여러 개 걸치면 전부). 분류가 곧 "무엇을 깊게 읽을지"를 결정한다 → Step 4.
여러 역할이면 전부 식별하고, 각각을 **별도 트랙**으로 본다 (병렬 후보 — Step 4 / `parallel-work.md`).

### Step 1.5. 파이프라인 선언 (절대 규칙 #15 — 모든 명령 필수)
**무엇을 하기 전에**, 이 작업이 4단계 파이프라인의 어느 단계에 닿는지·상위 단계 근거가 무엇인지 선언한다. 양식·예시·체크는 `docs/01-rules/design-pipeline.md` §2.

```
[파이프라인 선언]
- 닿는 단계: [□ 브랜딩  □ 디자인  □ 컴포넌트  □ 적용]
- 상위 근거: <파일 경로 / 시안 페이지 / 카탈로그 항목>
- 재사용:    <카탈로그에서 무엇을 재사용 / 없으면 신규 컴포넌트 X 등록 계획>
- 환류:      <신규 컴포넌트 시 카탈로그·쇼케이스·SCSS·뷰 4곳 동시 갱신 약속>
```

"상위 근거"가 비어 있거나 추측이면 **즉시 중단** 후 사용자에게 보고. 단계를 건너뛰는 작업은 일관성·재사용 자산화를 깬다.

### Step 2. 명확도 판정 → 분기
| 명령 상태 | 처리 |
|---|---|
| **명확 + 작음** (diff를 한 문장으로 설명 가능: 오타·로그 추가·변수명·문구 변경 등) | 양식·plan 생략. **바로 실행** |
| **어느 정도 구체적** (역할·목표는 분명, 범위·방법 디테일은 부족) | Step 3의 **작업 명세**로 정리 → 사용자에게 빠르게 확인 → 실행 |
| **모호함** (뭘 원하는지/어느 영역인지 애매) | **추측 금지.** `AskUserQuestion`으로 핵심만 질문. 범위가 클 것 같으면 **plan 모드**로 (탐색은 최소 토큰 — 필요시 서브에이전트에 위임) |

> plan 모드는 오버헤드가 있다. **다파일 변경·접근법 불확실·낯선 코드**일 때만. 작고 명확하면 그냥 한다.

### Step 3. 작업 명세 (구체적인 명령을 받았을 때 AI가 자동으로 정리하는 양식)

```
## 작업 명세
- 역할: <개발/퍼블/디자인/기획/브랜딩/서버 — 깊게 읽을 에이전트 파일>
- 목표: <한 줄: 무엇을, 왜>
- 범위 In: <건드릴 것>
- 범위 Out: <안 건드릴 것 / 다음으로>
- 참고: <파일·기존 패턴·시안·문서 (없으면 "탐색 필요")>
- 검증: <"됐다"를 어떻게 확인하나 — 테스트/스크린샷/빌드/체크리스트 항목>
- 우선순위: <긴급+중요 / 중요 / 간소화 / 나중에>
- 불확실: <모호한 점 — 있으면 여기서 질문하거나 plan>
```

- 사용자가 위 항목을 다 안 줘도 OK — AI가 채워서 보여주고 **빈칸·불확실 항목만 확인**받는다 (전체 재질문 금지).
- 작고 명확한 명령엔 이 양식을 만들지 않는다 (그게 더 낭비).
- `/task` 커맨드로 이 절차를 명시적으로 돌릴 수 있다.

### Step 4. 선택적 읽기 (토큰 절약의 핵심)
- **항상(가벼움)**: `CLAUDE.md` → `goals.md` → `client-info.md` → `patch-notes.md` 최근 3개
- **깊게(전체)**: Step 1에서 분류된 역할의 `.claude/agents/<role>.md` + 그 작업에 직접 관련된 docs만
- `must-check.md`는 **해당 카테고리(A~H)만** — PRE 항목 점검
- **읽지 않음**: 무관한 역할 에이전트, 무관한 docs, 과거 히스토리(검색할 때만)
- 탐색량이 많으면(여러 파일/넓은 범위) → **서브에이전트에 위임**해 메인 컨텍스트를 더럽히지 않는다
- 작업이 **여러 트랙**이면 → 각 트랙 **쓰기 범위 선언** → 비겹침이면 **병렬 디스패치**(1트랙=1에이전트), 겹침·레이어 의존·공유상태·`docs/04-history/*` 쓰기면 **직렬**. 판정 기준·디스패치 양식: `docs/01-rules/parallel-work.md`

### Step 5. 실행 → 기록
작업 수행 → POST 체크리스트 점검(`/checklist`) → `patch-notes.md`에 1줄 기록(`/patch-note`).

## 2. 작업 시작 순서 (READ ORDER) — 요약

`CLAUDE.md` → `goals.md` → (분류) → `roles.md` + 해당 역할 에이전트 파일 → `must-check.md` 해당 카테고리 → `client-info.md` → `patch-notes.md` 최근 3개 → 작업 → `patch-notes.md` 기록.
*(무관한 문서는 건너뛴다 — 토큰 절약. `CLAUDE.md` §0 참고)*

## 3. 우선순위 (긴급/중요 매트릭스)

| 분류 | 처리 순서 | 예시 |
|---|---|---|
| 긴급 + 중요 | **즉시** | 배포 장애, 보안 이슈, 고객 핫픽스 요청 |
| 중요 + 비긴급 | **계획적** | 기능 추가, 리팩토링, 문서화 |
| 긴급 + 비중요 | **위임/간소화** | 단순 수정, 텍스트 변경 |
| 비긴급 + 비중요 | **나중에** | 미관 개선, 미사용 코드 정리 |

## 4. 의사결정 권한

| 상황 | 결정 주체 |
|---|---|
| 코드 컨벤션 위반 사소한 수정 | AI 자체 판단 |
| 기능 동작 변경 | **사용자 확인 필요** |
| 디자인/브랜딩 변경 | **사용자 확인 필요** |
| 의존성 추가/제거 | **사용자 확인 필요** |
| 배포 관련 작업 | **사용자 확인 필요** |
| 고객 원본 자료 삭제 | **절대 금지** |

## 5. 막혔을 때 / 모호할 때

1. `docs/04-history/decisions.md`에 비슷한 결정이 있는지 확인
2. 관련 역할의 에이전트 파일에서 가이드 확인
3. 그래도 모르면 **추측 금지** → `AskUserQuestion`으로 질문, 또는 plan 모드
4. 같은 걸 2번 이상 잘못 고쳤으면 → 컨텍스트가 오염된 것. 사용자에게 `/clear` 후 더 구체적인 명령으로 다시 시작 권유
5. 병렬 트랙이 같은 파일을 건드린 게 보이면(`git status`로 확인) → 그 트랙들 직렬로 재작업. 트랙 산출물이 서로 모순되면 상위 레이어 트랙을 정본으로 (`parallel-work.md`)
