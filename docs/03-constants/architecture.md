# 아키텍처 · 코드 배치 규칙 (재사용 가능 상수)

> "코드를 **어디에 · 어떻게** 두는가"의 정본. 거의 변하지 않는다 — 다른 프로젝트로 그대로 복사.
> 한 줄: **루트를 더럽히지 마라. 새 폴더·파일을 함부로 만들지 마라. 묶을 수 있으면 묶어라(애그리거트). 상속보다 합성, 구상보다 인터페이스.**

---

## 0. 절대 원칙 (요약 — 어기면 작업 보류)

1. **루트 비대화 금지** — 프로젝트 루트(`/`)와 새 "최상위 폴더"를 만들지 않는다. 모든 PHP 코드는 `app/` 아래 적절한 네임스페이스에. 새 최상위 개념이 필요해 보이면 **먼저 기존 폴더에 들어갈 자리를 찾는다**. (`framework/` = 프로젝트 무관 인프라만 — 이 사이트 고유 도메인 금지.)
2. **SOLID** — SRP(한 클래스 한 책임), OCP(새 케이스는 `if/switch` 추가가 아니라 **새 구현체 + 레지스트리 등록**), LSP, ISP(좁은 인터페이스 여러 개), DIP(구상 클래스 말고 인터페이스/추상에 의존, **생성자 주입**).
3. **재사용 우선** — 기능을 추가할 때 같은 일을 하는 클래스가 이미 있으면 **거기에 메서드/구현체를 더한다**. 새 파일 만들기 전에 `app/Services`, `app/Site`, `app/Support`, `framework/` 를 먼저 본다.
4. **애그리거트로 묶기** — 관련 있는 여러 클래스가 흩어지면 **애그리거트 루트** 하나를 만들어 통합하고, 외부는 루트를 통해서만 접근한다(내부 엔티티 직접 생성·수정 금지, 불변식은 루트가 보장). 예: `Framework\Menu\Menu`(루트) → `MenuItem`(내부) · `App\Site\Works\Sectoins\SectionRegistry`(루트) → `SectionDefinition`.
5. **부분-전체 합성** — 상속보다 합성. 큰 객체는 작은 협력 객체들을 **조합**해서 만든다 (`LighthouseManager` ← 여러 `*Inspector` 처럼). 깊은 상속 트리 금지.
6. **인터페이스 우선** — 협력 지점은 인터페이스(`Contracts/`)로 정의하고 거기에 의존한다. 구현 교체·테스트 더블·기능 토글이 자연스러워진다.

> DDD 세부(애그리거트 경계, 도메인 이벤트, 유비쿼터스 언어, 데이터 설계)는 `.claude/agents/developer.md`. 이 문서는 **"어디에 두나 + 새 기능 추가 절차 + 모듈=토글 단위"** 가 본업.

## 1. 코드를 어디에 두나 (`app/` 맵)

| 무엇 | 어디 | 비고 |
|---|---|---|
| HTTP 입출력만 (요청 검증·응답·리다이렉트·직렬화) | `app/Controllers/<영역>/` | **로직 금지** — 서비스/도메인 호출만. 컨트롤러 공통은 `app/Concerns/<영역>/` 트레이트 |
| 비즈니스 로직·유스케이스 | `app/Services/<영역>/` | 한 클래스 한 책임. 흩어진 절차를 모은 곳 |
| 도메인 모델(데이터 **+ 행동**) | `app/Models/<영역>/` | anemic model 금지 — 행동을 모델 안에 |
| 도메인 모듈 (애그리거트·정책·정의·레지스트리 묶음) | `app/Site/<모듈>/` 또는 `app/<모듈>/` | **한 기능 = 한 폴더 = 한 네임스페이스**. 그 안에서 `Contracts/` `Dto/` `Support/` 로만 갈래 침 |
| 인터페이스·계약 | `app/<모듈>/Contracts/` (모듈 전용) 또는 `app/Contracts/` (전역) | DIP의 "추상" |
| DTO·값 객체 | `app/<모듈>/Dto/`, `app/Support/` | 불변 우선 |
| 열거형 | `app/Enums/` | |
| 헬퍼·순수 유틸 (상태 없음) | `app/Support/`, `app/Helpers/` | |
| 서비스 프로바이더 (바인딩·부트) | `app/Providers/` | 새 모듈은 자체 Provider 1개 가능 |
| 프레임워크 레벨 (프로젝트 무관) | `framework/<영역>/` | 이 사이트 고유 도메인은 절대 금지 |
| 일회성 CLI 스크립트 | `scripts/` | 파일명 `YYMMDD-HHMM-제목` (`conventions.md`) |
| 라우트 | `routes/{web,admin}.php` | 모듈이 늘면 모듈별 등록 메서드/파일로 분할 |
| 설정 | `config/<이름>.php` | 비밀값 금지 → `.env` |
| 마이그레이션 | (마이그레이션 러너 디렉터리 — §4) | `YYMMDD-HHMM-제목`, 한 파일 = 한 변경 |

- **새 최상위 폴더가 정말 필요한가? 거의 아니다.** 새 도메인 모듈이면 `app/<Module>/` **딱 하나**. 진입점은 폴더가 아니라 그 안의 **애그리거트 루트 클래스**.
- 깊이 4단계 이하 권장. `index.{ext}` 류 없이 클래스 네임스페이스로 진입.

## 2. 기능을 추가할 때 (절차) — `/task` · `must-check.md` B 와 함께

1. **있는 걸 찾는다** — 같은 일을 하는 클래스/서비스/모델/프레임워크 컴포넌트가 이미 있나? 있으면 **거기에 메서드·구현체 추가**. 새 파일 만들지 않는다.
2. **관련은 묶는다** — 새로 만들 것이 기존 여러 클래스와 한 묶음이면 → **애그리거트 루트를 만들거나 기존 루트에 흡수**. 흩뿌리지 않는다. (둘 이상의 클래스가 항상 같이 다니면 묶을 신호.)
3. **확장은 구현체로 (OCP)** — 새 "종류"(섹션 타입, inspector, 결제수단, 운영 액션…)는 공통 **인터페이스/추상의 새 구현체** + 레지스트리에 등록. 기존 코드에 `if/switch` 분기 추가 금지.
4. **합성으로 조립** — 큰 기능 = 작은 협력 객체 조합. 의존은 **생성자 주입**, 타입힌트는 인터페이스.
5. **새 모듈이면** — `app/<Module>/` 폴더 1개 (+ 필요시 `Providers/<Module>ServiceProvider`). 컨트롤러는 `app/Controllers/...`, 라우트는 `routes/...`, 서비스·애그리거트는 모듈 폴더. **그리고 기능 토글 레지스트리에 등록**(§3) — 이게 빠지면 미완성.
6. **마이그레이션이 필요하면** — 정식 마이그레이션 러너로(§4). raw `.sql` 을 DB에 직접 꽂지 않는다.
7. **PRE/POST 체크** — `docs/01-rules/must-check.md` B 카테고리.

## 3. 모듈 = 기능 토글 단위 (라이선스 스위칭) ⭐

이 프로젝트는 기능을 **토글로 켜고 끄는** 구조다 — 고객사별로 라이선스/유료 활성화해서 운영하는 비즈니스 모델. 그래서 **기능 = 토글 가능한 모듈** 이 설계 단위다.

- **모든 기능 모듈은 자기 자신을 "기능 플래그"로 선언하고 레지스트리에 등록한다.**
  (구현체는 운영콘솔 단계에서: `App\Platform\Features\FeatureRegistry` 애그리거트 + `config/features.php`(정의) + DB `feature_flags`(켜짐 상태). → 구현 로드맵 참조. 정의가 생기기 전까지 이 절은 *규칙*만 명시.)
- **플래그가 꺼지면 — 하드 차단**: 그 모듈의 **라우트는 등록 자체를 안 하거나 미들웨어로 404**, 사이드바 메뉴/링크도 숨김. → **라우트 등록과 메뉴 렌더가 둘 다 같은 플래그를 조건**으로 한다 (한쪽만 막으면 안 됨).
- **모듈이 많아지면 그룹 → 하위 항목 2단계**로 묶는다. 예: `work` 그룹 → `work.templates` · `work.canvas` · `work.thumbnails`. config 토글 페이지·관리자 사이드바 **둘 다** 이 그룹 구조로 렌더 → 가독성.
- **새 기능 모듈을 만들면 → 반드시 기능 플래그 정의에 추가**한다: `key` · `label` · `group` · `default`(기본 on/off) · `routePrefix`(들) · `menu`(사이드바 위치·아이콘). **이걸 빼면 그 기능은 토글 페이지에 안 보이고 라이선스 비즈니스에서 누락된다.** (`must-check.md` B 에 항목으로 포함.)
- 플래그 키는 `kebab.dotted` (예: `name-market`, `work.canvas`). 절대 코드 곳곳에 문자열로 흩지 말고 `FeatureRegistry` 통해 조회.

### §3.1 기능 제거 시 (Removal Protocol) — CLAUDE.md 절대 규칙 #9 의 본문

기능을 더 이상 노출하지 않기로 결정했을 때 **코드를 삭제하지 않는다**. 다음 절차를 따른다:

1. **`config/platform/features.php` 의 해당 키** `'default' => false` 로 변경하고 `'desc'` 에 폐기 결정 일자·사유 1줄 추가.
2. **DB `feature_flags`** 에 `enabled = 0` 으로 row 명시 (`/console/features` 에서 토글로 즉시 반영). 이로써 `FeatureGate` 미들웨어가 해당 `route_prefixes` 의 모든 요청을 404 처리한다.
3. **뷰·메뉴 렌더링 코드의 `feature_enabled('<key>')` 가드** 가 이미 있는지 확인 — 없으면 추가. **푸터·사이드바·헤더·드로어 모두 점검**(어느 한 곳이라도 `route()` 직접 호출이 남아 있으면 풋더 렌더가 RoutingException 으로 죽는다 — 2026-05-19 사고 사례).
4. **데이터·마이그레이션**: 테이블·컬럼은 그대로 둔다. 추후 재활성화 시 데이터 손실 방지.
5. **patch-notes.md 기록**: "feature `<key>` 토글 OFF — <사유>" 1줄.

복귀(재활성화)는 step 1 의 `default` 를 `true` 로 되돌리거나 토글 UI 에서 ON 만 하면 끝 — *코드 변경 없음*. 이게 토글 아키텍처의 본질이다.

**예외**: 타프로젝트 잔재 코드(잘못 복사된 파일)는 이 규칙 적용 대상이 아니다. 이 프로젝트 자체 기능이 아니므로 보존 가치가 없다 — patch-notes 에 "타프로젝트 잔재 정리" 명기 후 삭제 가능.

## 4. DB 마이그레이션

- 스키마/데이터 변경은 **마이그레이션 러너로만**. 적용 이력을 `migrations` 테이블에 기록한다 (파일명·배치·적용시각).
- 2026-09-16: console 인증 스키마는 `database/migrations/260916-0845-create-admin-schema.php`로 적용. `nb_admin`·`nb_roles`·`migrations`를 생성하며 관리자 계정은 시드하지 않는다.
- 마이그레이션 파일: `YYMMDD-HHMM-제목` (`conventions.md`), **한 파일 = 한 변경**, 가능하면 `down`(되돌리기) 포함. 하위호환 순서 지킴(컬럼 추가 → 배포 → 코드 전환 → 삭제).
- 기존 `resources/sql/*.sql`(과거 백업·1회성 덤프)은 그대로 두되 **앞으로의 스키마 변경은 마이그레이션으로**. 운영콘솔에 "마이그레이션 실행 / 백업" 버튼 (구현 로드맵).
- DB 접속값은 `config/database.php`(+`.env` 오버라이드). **마이그레이션 실행 전 자동 백업.**
- 로컬↔운영 모두 같은 마이그레이션을 적용 → 환경 간 스키마 드리프트 0.

## 6. 안티패턴 (하면 안 되는 것)

- 루트나 새 최상위 폴더에 파일 생성 / `app/` 맵 무시하고 아무 데나 클래스
- 기존에 같은 일 하는 클래스가 있는데 새로 또 만듦 (중복)
- 관련 클래스들을 흩뿌리고 애그리거트 루트 없이 서로 직접 호출
- 새 "종류"를 기존 코드 `if/switch` 분기로 추가 (OCP 위반)
- 구상 클래스를 직접 `new` 해서 강결합 / 인터페이스 없이 협력
- God class·God service (책임 5개짜리 클래스), 깊은 상속 트리
- 새 기능 모듈인데 기능 플래그 등록 누락 → 토글 페이지·라우트 게이트에 안 보임
- 스키마를 raw `.sql` DB 직접 실행으로 변경 (마이그레이션 우회)
