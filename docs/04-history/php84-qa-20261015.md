# PHP 8.4 마이그레이션 검증 기록 — 2026-10-15

## 판정

수정본은 PHP 8.3.35·8.4.26의 격리 서버 기능 QA를 통과했다. **화면 QA는 도구 초기화 오류로 미완료이며, 운영 배포 완료나 무조건적 전체 호환을 뜻하지 않는다.** 운영 파일·DB·Git 원격은 변경하지 않았다.

## 적용한 규칙과 실제 확인 파일

- #16: patch-notes에 요구사항·6분야 영향·8개 계획을 먼저 남겼고, 구현 후 아래 증거와 배포 문서를 기록했다.
- #2: `inc/lib/helper/ImageHelper.php` 안에서만 Intervention v2→v3 API를 교체했다. 호출자인 `inc/lib/func.php`, `console/pages/board/ajax/board.process.php`, `console/pages/board/ajax/upload.php`, `scripts/backfill-webp.php`의 기존 계약을 확인했다.
- #9: 미사용 SmartEditor2/jbimages 폴더는 보존하고 루트 `.htaccess`에서 웹 진입을 차단했다. Summernote는 유지했다.
- #4/#8: 기존 소개서·게시판의 HTTP 메서드, `_method` 삭제 계약과 JSON 응답을 변경하지 않고 HTTP 회귀로 확인했다.
- `composer.json/lock`, `dockerfile`, `.dockerignore`: PHP 8.4 빌드·확장·의존성 범위. `config/setup.php`, `.user.ini`, `apache.conf`: 운영 환경과 기존 업로드 한도.
- `inc/lib/base.class.php`: 선택 include 존재 여부. `inc/lib/site.info.php`: CLI에서 없는 HTTP 메타 기본값.
- `console/lib/QA/CrudQaInspector.php`: 명시적 nullable callable. `console/pages/board/board.view.php`: NULL depth 값의 안전한 문자열 처리.

실행 위치는 별도 `qa-php-20261015`이며 Compose 프로젝트는 `partnerit-phpqa-20261015`다. repo는 읽기 전용 마운트, DB와 uploads는 격리했다.

소개서 세부 검증: 잘못된 CSRF 403, 필드 검증 422, 정상 접수 201, 중복 제출 DB 증가 1건, PDF 200(5,300,167 bytes), 다른 세션 다운로드 403, 횟수 제한 429. 테스트 메일은 MIME만 생성했고 외부 SMTP를 발송하지 않았다.

`APP_ENV=production` 검사는 실제 자격 증명 대신 빈 .env + 테스트 DB 환경 변수로 수행한 **로컬 시뮬레이션**이다. 실제 호스팅 검사가 아니다.

## 미완료·잔여 리스크

- 공식 브라우저 도구가 `failed to write kernel assets (os error 3)`로 초기화 실패. 세션 reset 후 동일 실패. 데스크톱/모바일 화면·JS 상호작용 QA는 통과 처리하지 않았다. Codex 재시작 후 UI 검증 필요.
- 실서버 SAPI(FPM 등), 확장, 파일/세션 권한, SMTP, OPcache는 미확인. 전환 전 호스팅 환경에서 server-spec 체크 필요.
- Imagick 드라이버는 미검증. 검증 환경과 동일하게 GD를 쓰거나 별도 Imagick 회귀 수행.
- 새 Composer vendor는 최소 PHP 8.3을 요구한다. PHP 7.4 서버에 이 vendor만 먼저 덮어쓰면 사이트가 중단될 수 있다.
- 구형 에디터는 전체 기능을 이식한 것이 아니다. 문법 보정 및 웹 접근 차단만 했다. 해당 경로 재활성화 금지.
- root vendor와 resource/vendor는 Git ignore 대상. Git 소스만 올려서는 라이브러리/레거시 보정 파일이 전부 배포되지 않는다. lock 기반 install 또는 검증한 vendor 패키지가 필요하다.

## 전환 산출물

서버용 후보 묶음에는 변경 런타임 파일과 새 vendor 전체만 포함한다. `.env`, DB 덤프, uploads, 테스트 계정·fixture, 기존 프런트 dist, Docker 및 문서는 웹 루트 업로드에서 제외한다. UI 검증과 서버 준비 후 사용하며, 기존 vendor를 백업하고 통째로 교체한다. 상세 순서는 `docs/00-overview/server-spec.md` 참조.

공식 API 근거: [PHP 8.4 deprecations](https://www.php.net/manual/en/migration84.deprecated.php), [Intervention v3 drivers](https://image.intervention.io/v3/basics/configuration-drivers), [resize](https://image.intervention.io/v3/modifying-images/resizing), [output](https://image.intervention.io/v3/basics/image-output).

## 최종 판정 — 2026-10-15 브라우저 복구 후 검수 완료

이 항목은 위의 **화면 QA 미완료 판정을 대체**한다. Codex 재시작 후 공식 내장 브라우저가 정상 작동하여 PHP 8.4.26 격리 서버에서 아래 검증을 완료했다. PHP 8.4 전환용 소스·의존성 정리 및 로컬 QA는 완료했으며, 운영 배포는 수행하지 않았다.

- 공개 9페이지(`/`, `/about/company`, `/matching`, `/ai-report`, `/consortium`, `/pricing`, `/partners`, `/legal/privacy`, `/legal/cookies`)를 320·390·768·1440px에서 확인했다. 36개 DOM 측정 모두 제목 존재, 깨진 이미지 없음, 문서 가로 넘침 없음. 390·1440px는 등장 모션 종료 후 캡처하고 화면을 직접 검토했다. 모든 브라우저·기기에서의 완전한 호환성을 의미하지 않는다.
- 모바일 메뉴 열기 → AI 보고서 이동 → 메뉴 닫힘 확인. 고객사례 `/partners/6`의 DB 본문·이미지·목록 링크와 390px 화면도 확인했다.
- 소개서 PC 신청·완료, 닫은 후 재진입 시 폼/동의 초기화, 모바일 모달 내부 스크롤 및 390px 신청·완료 UI를 확인했다. 모바일 제출은 첫 시도에 정상 완료했다. 테스트 정보만 격리 DB에 저장했고 실제 고객 문의나 외부 메일은 발송하지 않았다.
- PC 첫 신청은 서버 201 이후 화면에 일시적 연결 오류가 표시되었다. 실제 상태를 확인한 뒤 같은 요청을 재시도해 완료했고, DB는 1건으로 유지되었다. 원인은 확정하지 않았다. 후속 모바일 첫 제출 성공 및 기존 idempotency/HTTP 검증과 함께 기록하며, 이를 임의의 애플리케이션 수정 근거로 삼지 않았다.
- QA uploads에만 빠져 있던 기존 게시물 이미지 3개를 원본 로컬 uploads에서 복사하여 DB fixture와 맞췄다. 원본 uploads·운영 데이터는 변경하지 않았다.
- UI 확인 후 브라우저 error/warn 로그는 비어 있었고, E_ALL PHP 오류 기록도 없었다. Apache error log의 3건은 앞서 의도적으로 요청한 보호 경로 403 기록이다.
- 증거: 별도 `qa-php-20261015/screenshots/ui-results.json`(18건), `boundary-results.json`(18건), PC/모바일 캡처 및 `brochure-complete-mobile.jpg`. 캡처와 QA fixture는 웹 루트 배포 대상이 아니다.

### 최종 산출물과 운영 전제

`release/php84-migration-final-20261015.zip`의 `upload/` 내부만 사이트 루트에 적용한다. 변경 런타임 11파일과 root vendor 전체(합계 498파일)를 포함하며, 후보 검증 후 런타임은 추가 변경하지 않았다. 신규 SQL·CSS/JS 빌드는 필요 없다. README와 QA.md는 업로드하지 않는다.

실제 호스팅의 PHP 8.4, 확장, 세션/업로드 권한, OPcache, SAPI, SMTP는 여전히 운영 전 확인 대상이다. Imagick은 검증하지 않았으므로 검증된 GD 사용을 기준으로 한다. PHP·소스·vendor를 함께 전환하고 기존 vendor와 혼합하지 않는다. 운영 서버 접속·배포·Git push는 하지 않았다.
